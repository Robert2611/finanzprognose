## B-005 Define an explicit, language-neutral API contract (and make backend output testable)

- **Status:** done (all 4 phases complete — see below)
- **Problem:** The API has no defined contract — it exposes the storage model directly. `GET /api/state` returns raw table rows (`db.all_rows`), including internal fields (`created_at`, `updated_at`, `archived` as 0/1), integer-cent amounts and opaque German `kind` keys, so the wire shape *is* the schema: adding or changing a column changes what every consumer and every test sees. This causes three coupled problems:
  1. **Language leaks from the backend.** German text is produced in Python and shown verbatim by the frontend: API error messages (`detail`, including Pydantic validator messages in `main.py` and `NotFound`/`Conflict` in `db.py`), the DB trigger messages, forecast `warnings`, `explanation` lines and item labels in `forecast.py` ("Startstand (Ist-Stand)", "Grundbetrag …"), and backup errors and run reasons ("manuell", "zeitplan") in `backup.py`. Two German strings are also stored in the database: the checkpoint note "Startstand bei Anlage" (`main.py`) and the audit comment "Rückgängig gemacht: Protokolleintrag #n" (`db.py`). The account `kind` values (`giro`, `tagesgeld`, `depot`, `kreditkarte`, `bar`, `sonstiges`) are German identifiers stored in existing databases.
  2. **The frontend has to understand storage encodings** (divide cents, re-map `kind` via `KINDS`, interpret `archived` as 0/1), which is what makes the language leak feel natural and lets it spread.
  3. **The output is hard to test.** There is no stable, named shape to assert against — tests must rummage through the full `/api/state` dump, and any schema change breaks them. `forecast.compute()` is the counter-example: a pure function with a defined output that is trivially testable.
- **Target:** The API speaks a stable, language- and presentation-neutral contract — language-neutral codes + params out, defined response shapes that don't track schema churn — and `app.js` owns 100% of the human text and formatting (it already has `ENTITY`/`ACTION`/`FIELD`/`KINDS`/`RHYTHM`). Keep the generic `TABLES`-driven CRUD engine internally; the write path is already validated via `MODELS`, so this is about defining the *output*, not replacing the engine. Integer cents stay on the wire (correct for money); only labels/encodings that exist purely for display move out.
- **Approach — do it in four independent phases, each its own session and commit, tests green at every step** (one mega-change accumulates a large billed context and is risky; small phases stay cheap and safe):
  - **Phase 1 — Error envelope.** Replace ad-hoc German `detail` strings with a consistent machine-readable envelope `{code, params}` for validation / `Conflict` / `NotFound` (`main.py` handlers + `db.py` exceptions). `app.js` (`api()` in the helpers section) maps codes → German. *Done:* no German in error responses; the UI shows the same messages.
  - **Phase 2 — Response models + contract tests. Done.** Added `app/contracts.py` with Pydantic response models (`AccountOut`/`EntryOut`/`AdjustmentOut`/`CheckpointOut`, `StateResponse`, `AuditEntryOut`, `BackupStatusOut`/`BackupFileOut`) and wired them as `response_model` on `/api/state`, `/api/audit` and `/api/backup/status`. `created_at` is dropped and `archived` is now a real boolean on the wire; `/api/forecast` and the write endpoints are untouched (forecast codes are Phase 3; write responses were out of scope). `tests/test_app.py` gained `test_state_contract` (asserts the exact key set, checks `archived` is a bool, and proves a column added directly to the table via `ALTER TABLE` does not leak into `/api/state`), `test_audit_contract` and `test_backup_status_contract`.
  - **Phase 3 — Forecast codes. Done.** Turn forecast `warnings`, `explanation` lines and item labels into codes + params (e.g. `{"code": "base_amount", "amount": -60000}`); `app.js` (`drawDetail`/`renderForecast`) renders them. Keep the derivations accurate — showing them is a core feature. *Done:* no German in `forecast.py`; explanations render identically.
  - **Phase 4 — Stored strings + `kind` labels. Done.** Store neutral values for the checkpoint note and the revert audit comment going forward, and keep rendering the old German values for existing rows (backward-compat). Treat renaming the `kind` values as a data migration (now unblocked by **B-002**), or keep them as opaque keys and only localize their labels. *Done:* no new German stored; an upgraded production DB still renders correctly.
- **Resolution (phase 1):** `db.NotFound`/`db.Conflict` now carry a `code` plus `**params` (e.g. `NotFound("not_found", entity=table, id=id_)`) instead of a formatted German sentence. `main.py`'s exception handlers for both, plus a new one for `HTTPException`, emit a `{"code": ..., "params": {...}}` body (falling back to the plain `{"detail": ...}` shape only for framework-internal exceptions that don't carry our envelope). The custom `model_validator`s in `EntryIn`/`AdjustmentIn` now raise `ValueError(<short code>)` instead of German sentences; `_validation_detail()` turns any `pydantic.ValidationError` into `{"code": "validation_error", "params": {"errors": [{field, code, params}, ...]}}`, using Pydantic's own machine-readable `type`/`ctx` for built-in constraint violations. `app.js` adds `VALIDATION_CODES`/`ERROR_CODES`/`errMsg()` to map every code back to the exact German text the UI showed before, reusing the existing `ENTITY`/`FIELD` maps (added an `audit_log` entry to `ENTITY`). Verified via a manual run that every error path (`unknown_table`, `validation_error`, `not_found`, `conflict`, `ref_not_found`, the custom codes, and the audit-revert `not_found`) round-trips to the original German message.
- **Resolution (phase 3):** `forecast.amount_at()` now returns `explanation` as a list of `{code, params}` dicts (`base_amount`, `set_amount`, `percent_change`) instead of German sentences; `compute()`'s `warnings` list does the same (`transfer_target_archived`, `no_checkpoint`), using ids (`entry_id`/`account_id`) as params rather than names, since names can be resolved client-side and ids survive renames. The checkpoint item labels ("Startstand (Ist-Stand)" / "Ist-Stand eingetragen") were dropped entirely rather than turned into a code — the frontend already branches on the presence of `deviation` for the explanatory text below the row, so it derives the label from that same existing field. The now-unused `format_eur`/`format_date_de` helpers were deleted. `app.js` adds `EXPLANATION_CODES`/`explLine()` and `WARNING_CODES`/`warnMsg()` (same `{code, params} -> German` pattern as phase 1's `ERROR_CODES`), plus an `entryName()` lookup alongside the existing `accName()`, and a zero-padded `fFull()` date formatter (the existing `fDate()` doesn't zero-pad, which would have changed the rendered text). `tests/test_app.py`'s explanation assertion now checks `e["code"] == "set_amount"` instead of a German substring. Verified via a manual forecast run (base/set/percent-yearly explanations and both warning codes) that the rendered German text is byte-identical to before.
- **Resolution (phase 4):** Given the app has not shipped yet (no deployed database with real rows), the backward-compat and data-migration concerns in the phase description turned out to be moot, so the fix is simpler than scoped: (1) `kind` values are renamed directly in `main.py`'s `Literal`, `db.py`'s `DEFAULT`, and `app.js`'s `KINDS` map (`giro→checking`, `tagesgeld→savings`, `depot→custody`, `kreditkarte→credit_card`, `bar→cash`, `sonstiges→other`) — no migration needed since `SCHEMA` is still the only version ever created. (2) The checkpoint note "Startstand bei Anlage" is no longer stored at all — `main.py`'s auto-created checkpoint now gets `note: ""`, and the Accounts view (`app.js`) derives the same label structurally (earliest non-archived checkpoint per account) and renders it as a "Startstand" tag, instead of round-tripping a stored string through a field that's otherwise free-form user text. (3) The revert audit comment is no longer stuffed into the free-text `comment` column either — `audit_log` gained a `reverts_id INTEGER` column (added directly to `SCHEMA`, not a migration), set by `db.revert()` and exposed via `AuditEntryOut.reverts_id`; `app.js`'s audit view renders "Rückgängig gemacht: Protokolleintrag #n" from that column. `comment` is now reserved purely for user-entered reasons. Verified via the test suite (`test_audit_contract` updated for the new field, `test_optimistic_locking_and_audit` extended to assert `reverts_id` round-trips) and manually in the browser (Accounts view shows the "Startstand" tag, Verlauf shows the revert line).
- **Done when:** Read endpoints return defined, documented shapes that don't change when unrelated columns are added; no German text remains in `app/*.py` except in tests; the UI still shows the same German text; and backend output is covered by tests that assert against the contract rather than raw rows.
- **Related:** Pairs with **B-008** (frontend split + lit-html) — the frontend ends up owning all text/formatting, so the code→German maps live in the new `core.js`. Phases 1–3 are well-specified mechanical refactors (good fit for a cheaper model); phase 4 benefits from more care. Optionally start with a read-only inventory of every German string in `app/*.py`.

## B-008 Split app/static/app.js into smaller modules

- **Status:** done (both steps complete)
- **Problem:** `app.js` is a single 500+ line file covering everything: generic helpers, state, the generic form-dialog component, routing, and every view (forecast, entries, accounts, audit/history, backup). It already has clear comment-delimited sections, but they all live in one file. This violates the file-size preference in `CLAUDE.md`.
- **Proposal:** Two sub-steps, done in order:
  1. Split along the existing section boundaries into separate files (e.g. `core.js` for helpers/state/formDialog/routing, and one file per view: `forecast.js`, `entries.js`, `accounts.js`, `audit.js`, `backup.js`). Since the project has no build step, load them as native ES modules (`<script type="module">` with explicit imports/exports) rather than introducing a bundler. Behavior and rendering approach (`innerHTML` string templates) stay unchanged in this step.
  2. Replace the `innerHTML` string-template renders with lit-html: vendor a single lit-html ES module file (no CDN at runtime, no bundler) and convert each view's render function to a tagged `html\`...\`` template. This drops the manual `esc()` calls (lit-html auto-escapes text bindings) and the current pattern of re-querying/re-binding event listeners after every full-subtree replacement (e.g. the forecast chart/table row clicks), in favor of event bindings declared inline in the template.
- **Done when:** `app.js` no longer exists as one monolith, each new file has a single view/responsibility, views render via lit-html templates instead of `innerHTML` string concatenation, and the app works unchanged in the browser without any build step.
- **Resolution (step 1):** Split along the original section boundaries into `core.js` (helpers, the API-error and forecast-code → German maps, `S` state, `formDialog`/`archiveDialog`/`restoreRow`, and navigation/routing), `forecast.js`, `entries.js`, `accounts.js`, `audit.js` and `backup.js` (one per view), loaded as native ES modules (`index.html`'s script tag gained `type="module"`). `app.js` is now just the 8-line bootstrap (`load()` + `render()` + the backup-pill interval) that used to be the file's "Start" section. One subtlety: `core.js`'s router (`render()`) has to call each view's render function, and every view module imports shared state/helpers back from `core.js` — a straight one-directional split isn't possible without `core.js` depending on all five views. Resolved by importing the view renderers into `core.js` directly, accepting the import cycle: this is safe in native ESM because nothing at module-evaluation time touches those bindings (the dispatch only runs inside `render()`, called after the whole module graph has loaded), confirmed by a Node ESM import-graph check and an in-browser run. Verified with `python -m pytest -q` (9 passed, backend untouched) and a Playwright run against a live server: created an account, clicked through all 5 nav views, zero console/page errors, screenshots confirmed each view renders its data (forecast chart/table/detail, audit log, backup status). Rendering approach is unchanged — all views still build HTML via `innerHTML` string templates; step 2 (lit-html) is still open.
- **Resolution (step 2):** Vendored `lit-html` 3.3.3's single self-contained production build as `app/static/vendor/lit-html.js` (no imports of its own, fetched via `npm pack`, sourcemap comment stripped since the `.map` isn't shipped; its BSD-3 license text is kept alongside as `vendor/LICENSE-lit-html.txt`). Converted every `innerHTML` string template to a tagged `html\`...\`` (or `svg\`...\`` — see below) lit-html template rendered via `render()`, across `core.js` (including `formDialog`, which now drives field visibility/validation/busy-state off a small local `state` object re-rendered on every `input`/`change`, instead of mutating hidden DOM nodes after an initial `innerHTML` build) and all five view modules. Every `data-*` + `querySelectorAll(...).forEach(b => b.onclick = ...)` rebind-after-render pattern is gone, replaced by `@click=${...}` (etc.) bound inline in the template, closing over the row/record directly instead of re-parsing an id back out of a dataset attribute. All `esc()` calls are gone — lit-html's text and attribute bindings auto-escape — and `esc` itself was deleted from `core.js`. One bug caught during manual verification: the forecast chart's SVG (grid lines, axis labels, data line, clickable month rects) silently failed to render because sub-templates returned from `.map()`/ternaries for SVG children (`<line>`, `<text>`, `<path>`, `<rect>`) were tagged with `html` instead of `svg` — each nested template is parsed independently via its own `<template>`, so without a literal enclosing `<svg>` tag establishing context, the HTML parser creates them in the wrong namespace and the browser renders nothing. Fixed by using the `svg` tag for every such nested template (the outer `chartTpl`, which has a literal `<svg>` wrapper, can stay on `html`). Verified with `python -m pytest -q` (9 passed, backend untouched) and Playwright runs against a live server covering: account/entry/adjustment/checkpoint creation, archive/restore, audit-log revert, backup run, navigating all 5 views, clicking chart rects and table rows to change month selection — zero console/page errors throughout, and screenshots confirmed the chart (grid, axis labels, data line) and all other views render identically to before.

A command-line flag was considered and rejected: it is still read once per process, so it would not remove the per-test server start.
